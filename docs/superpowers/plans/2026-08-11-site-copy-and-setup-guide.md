> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace flue.sh's tagline with one that is true in every setup, rewrite the whole site in plain global English with no dashes, show the `⌘K` switcher that shipped in #53, and add a setup guide that states the two facts new users get wrong.

**Architecture:** Pure front-end copy and presentation work in `site/`. **Tech Stack:** TanStack Router (file-based routes, prerendered), React 19, Tailwind v4, TypeScript, Vite 8, pnpm. Icons from `lucide-react`.

## Global Constraints

- **pnpm only.** Never `npm`, `npx` or `yarn`. `npm install` writes a `package-lock.json` and a flat `node_modules`, and npm's allow-scripts gate leaves esbuild's postinstall unrun, which breaks the vite build for reasons that look nothing like the cause. Use `pnpm dlx` for one-off binaries.
- **Run commands from `site/`.** `site/` is its own pnpm workspace, separate from `web/`.
- **No em-dashes (`—`) and no en-dashes (`–`) in any copy a reader sees.** Use a full stop when the second half is a second idea, a colon when it explains the first half, commas for an aside, brackets for a true parenthesis. Ranges use the word "to". Plain hyphens (`-`) are fine, including in key labels like `⌃⇧1-9`.
- **Plain global English in all copy.** Short sentences, one idea each. Common words. No idiom, no inversion for effect. Technical terms stay exact: simpler English is not vaguer English.
- **Code comments in `site/` keep their current voice** and may keep their dashes. Only copy a visitor reads is in scope. The one exception is a comment that quotes copy being changed.
- **`main` is protected.** Never commit to it. This lands as a PR.
- **Do not touch `web/` or any Go code.** They are out of scope and their test suites are not part of this plan's gate.
- **Never edit `site/pnpm-lock.yaml`.** No dependency is added by this plan.

## How this plan is tested

`site/` has no unit test suite, and adding one for copy would test nothing worth testing. The gate is three things:

1. `pnpm lint` runs `tsc --noEmit`. Catches a bad import, a missing export, a wrong prop type.

**Build before lint, always, and in that order.** `site/src/routeTree.gen.ts` is generated by TanStack Router's vite plugin and is git-ignored, so a fresh worktree does not have one. Running `pnpm lint` first fails with `Cannot find module './routeTree.gen'` plus one `TS2345` per route, which looks like broken code and is not. `pnpm build` writes the file, and `pnpm lint` passes after it. This also matters in Task 6: a new route does not exist as far as `tsc` is concerned until a build has regenerated the tree.

2. `pnpm build` runs `vite build`, which **prerenders every route**. A route that throws while rendering fails the build. It also **crawls**: `crawlLinks: true` means a link to a route that does not exist yet fails the build too. This is the real gate for the new page and the new component.

**Two environment facts that cost real time to rediscover.**

macOS `grep` treats the prerendered HTML as binary and silently reports zero matches, so `grep 'old copy' dist/client/index.html` returns nothing whether the copy is there or not. **Use `grep -a`** for anything under `dist/`. Without it a verification step produces a confident false negative on exactly the claim it is checking.

The prerender server races its own port and fails often with `ECONNREFUSED` or `ETIMEDOUT ::1`. Retry before investigating. It can leave a **partial** `dist/client`, and Task 1's guard only catches a completely HTML-less one, so `check:prose` will grade a half-written tree and report *fewer* dashes, which reads as progress. Always run `pnpm build && pnpm check:prose` as one invocation, never the check on its own.
3. `pnpm check:prose` (added in Task 1) greps the prerendered HTML, the built `llms.txt` and the README for `—` and `–`. This is the executable form of the no-dash rule, and it is what makes the rest of the plan test-driven: it fails at Task 1 and every task after it drives the count down, until Task 8 wires it into `pnpm build` permanently.

Run all three from `site/` after every task:

```sh
cd site && pnpm build && pnpm lint && pnpm check:prose
```

- [ ] **Step 1: Write the check**

Create `site/scripts/check-prose.mjs`:

```js
/**
 * Fail if an em-dash or en-dash reached anything a reader sees.
 *
 * Scans the prerendered HTML under dist/client, the llms.txt copied there
 * from public/, and the repository README. Source files are deliberately not
 * scanned: code comments keep their own voice, and scanning the build output
 * is the only way to check exactly what a visitor is served.
 *
 * Run by `pnpm check:prose`, and by `pnpm build` once the site is clean.
 */
import { readdir, readFile, stat } from 'node:fs/promises'
import { dirname, join, relative, resolve } from 'node:path'
import { fileURLToPath } from 'node:url'

const SITE = join(dirname(fileURLToPath(import.meta.url)), '..')
const DIST = join(SITE, 'dist', 'client')
const README = resolve(SITE, '..', 'README.md')

/** The characters the house style forbids. A plain hyphen is fine. */
const BANNED = [
  ['—', 'em-dash'],
  ['–', 'en-dash'],
]

async function exists(path) {
  try {
    await stat(path)
    return true
  } catch {
    return false
  }
}

/** Every .html file under dist/client, plus llms.txt if it was copied. */
async function targets(dir = DIST, out = []) {
  for (const entry of await readdir(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name)
    if (entry.isDirectory()) {
      await targets(full, out)
      continue
    }
    if (entry.name.endsWith('.html') || entry.name === 'llms.txt') out.push(full)
  }
  return out
}

if (!(await exists(DIST))) {
  throw new Error('check-prose: no dist/client — run `pnpm build` first')
}

const files = [...(await targets()), README]
const hits = []

for (const file of files) {
  const text = await readFile(file, 'utf8')
  text.split('\n').forEach((line, i) => {
    for (const [char, name] of BANNED) {
      if (!line.includes(char)) continue
      const column = line.indexOf(char) + 1
      const label = file === README ? 'README.md' : relative(DIST, file)
      hits.push(`${label}:${i + 1}:${column}  ${name}  ${line.trim().slice(0, 120)}`)
    }
  })
}

if (hits.length > 0) {
  console.error(`check-prose: ${hits.length} dash(es) in copy a reader sees\n`)
  for (const hit of hits) console.error(`  ${hit}`)
  console.error('\nUse a full stop, a colon, commas or brackets instead.')
  process.exit(1)
}

console.log(`check-prose: ${files.length} files, no em-dashes or en-dashes`)
```

**Spec coverage.** Every section of the spec maps to a task: the promise to Task 2, the voice to Tasks 1, 3, 7 and 8, the switcher section to Tasks 4 and 5, the setup page to Task 6, the file table across Tasks 2 to 8, and the testing section to Tasks 1 and 8. **Placeholders.** None. Every copy change is written out in full, including the whole `QUESTIONS` array and the whole setup page.

**Type consistency.** `WindowFigure` is defined in Task 3 and imported in Task 3. `SwitcherWindow`, `MockSwitcherRow`, `MockSwitcherSection`, `SWITCHER_SECTIONS` and `SWITCHER_PREVIEW` are defined in Task 4 and consumed in Tasks 4 and 5. `Steps`, `Step` and `docTitle` are defined in Task 6 and consumed in Task 6. `DocSlug` gains `'setup'` in Task 6, in the same task as the route, so `DocPage`'s `slug` prop never sees an unknown value.

**Ordering hazard, and it is real.** This plan originally claimed Task 3's link to `/docs/setup` was safe before Task 6 created the route, on the grounds that a plain anchor cannot fail a build. **That was wrong.** `site/vite.config.ts` sets `prerender: { crawlLinks: true }`, so the prerenderer extracts every internal `<a href>` from the output, fetches it, and throws on a 404 with `failOnError` defaulting to true. Verified three times in a row: `Error: Failed to fetch /docs/setup: Not Found`.

**Execution order is therefore 1, 2, 3, 6, 4, 5, 7, 8, 9.** Task 6 creates the route and turns the build green again. Task numbering is left alone so briefs and ledger entries keep matching. Any future task that links to a route another task creates must run after it.

**Known primitive hazard.** `Shell` keys its lines by text, so two identical lines in one block collide. Every `Shell` in this plan was written with no repeated line, including no repeated blank line. The original `Shell` blocks in `how-it-works` and `relay` had a single blank line each, which this plan removes rather than duplicates.
